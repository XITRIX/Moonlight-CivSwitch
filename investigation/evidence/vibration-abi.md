# Vibration ABI, Civ VII 1.0.0 on Switch 2

Read-only capture on 2026-11-10 from 192.168.1.182, through CivHomebrew
0.4.3. `vibration-exports-switch.txt` records bounded export metadata and code
bytes. Inspection completed with `VIBRATION_INSPECT_DONE` and `Executed
successfully`. The launcher was restored afterward.

Observed signatures used by the implementation:

- `nn::hid::utility::GetVibrationDeviceHandles(Handle*, int* count, int capacity,
  unsigned int npadId, BitFlagSet<32,NpadStyleTag> style)` returns Result.
  Its instructions write handles in 4-byte increments and a 32-bit count.
- `nn::hid::detail::InitializeVibrationDevice(const Handle&)` returns Result;
  the public wrapper aborts on failure and is deliberately unused.
- `nn::hid::detail::SendVibrationValues(const Handle*, const VibrationValue*,
  int count)` returns Result and passes two pointer/count arrays to HID.

REA/Hopper analysis of the captured bytes in a temporary ELF:

- Handle enumeration: `ev_6e8f8e14bc2c61e07b392b2c3b51c2181ee58a7940fb909753fadb1e33350640`.
- Single send by-reference arguments: `ev_8bc8b6fa35334fbb7530d073ded68302dcea03e66861d625d2dcd8a174a3a996`.
- Array send: `ev_3165ce905e670857f20e369b1e0a1afdfc255b119a38d2678633a58be9d834c8`.

The ELF was assembled only from captured functions; gaps are zero-filled and
external callees are absent. Hopper reports section-relative addresses. These
observations establish call shapes, not physical vibration or end-to-end host
rumble. `VibrationValue` uses four little-endian float32 fields (low amplitude,
low frequency, high amplitude, high frequency), corroborated by the open-source
[libnx HID definitions](https://github.com/switchbrew/libnx/blob/master/nx/include/switch/services/hid.h).
The adapter uses 160 Hz and 320 Hz, scales the two unsigned 16-bit host strengths
to [0,1], and does not change the system vibration permission.

## Native adapter test

`vibration-pulse-switch.txt` records the production `controller-input.js` adapter
on the same console. It selected a connected Npad, obtained and initialized the
vibration handles, sent two 200 ms quarter-strength pulses (low and high bands,
separated by 150 ms), then sent zero amplitudes and closed its buffers. All
Result-returning calls succeeded; both the pulse completion and loader success
markers arrived. This verifies native submission and cleanup, not the user's
physical perception or rumble generated by a PC game during streaming.

The user reported hearing at least one vibration, but missed the full sequence.
Physical confirmation is partial; no game-generated rumble session was tested.

## Reported 50 Mbps stutter and native-call timing

After the user reported video stutter, `benchmark-vibration.js` measured the
production adapter on the idle console, with no stream running. The result in
`vibration-timing-switch.txt` has both completion markers. Across 60 changed
updates: mean 0.252 ms, p95 0.304 ms, maximum 0.436 ms. Initial handle setup plus
first send took 1.173 ms. Duplicate levels averaged 0.019 ms. These timings do
not bound calls under streaming load and do not establish the cause of stutter.

Previously the C rumble callback called native HID synchronously inside the
cooperative receive pump. The revised JS callback only stores the newest levels.
One combined update runs after video presentation/audio service, with nonzero
updates capped to 30 Hz. Zero strength bypasses the cap. Tests preserve the
50 Mbps receive budget and verify that 200 callbacks in a tick produce one
output after media processing. Runtime timing is recorded in RAM and shown in
the performance overlay. A saved Gamepad rumble setting disables capability
advertisement and output, allowing an on/off comparison in the same scene.
Actual improvement at 50 Mbps remains unconfirmed pending user playback.
